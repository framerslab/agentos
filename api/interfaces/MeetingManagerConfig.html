Optional scrubUnkeptOutbox

scrubUnkeptOutbox?: boolean

Whether the completion of a run kept nowhere (keep: 'none') empties the run's content deliveries in the outbox, pending and delivered ones, before the run is done, as a purge does: an outbox with sendClaimed also cancels the run's send under way, and a FencedOutbox stores every later delivery of the run without content. Default true. False leaves the run's deliveries to their retries, so a destination still receives the content deliveries pending at completion. The run's transcript and event payloads are removed either way, and a purge of the run empties its deliveries whatever this says.

Optional beforeComplete

beforeComplete?: ((run, turns) => Promise<void>)

Optional. The host's step before a run's settle and scrub, awaited with the run as it stands in left and every turn the run stored, once the transcript is fenced (no turn can arrive after it). A step that throws is logged by its error's name, and the completion goes on: the run ends done and a run not kept loses its content all the same. It is not run for a run the stop phrase or a purge ended, nor for a failed run (neither has turns to give). It runs once per run: the cleanup claims the run before the step (completionHookClaimedAt), so a tick's cleanup that overlaps a report's, or another instance's, waits for it rather than running it again, and the scrub of a run not kept comes after the step whichever cleanup finishes; a claim a stopped process left is taken over once it is COMPLETION_HOOK_LEASE_MS old.

Optional usageSilenceMs

usageSilenceMs?: number

End at the last durable usage after this silence. Omitted preserves the existing reconciliation policy. When set, a dispatching or dispatched run whose worker has sent no fresh usage report for this many milliseconds (counted from the manager's receipt of the last one, or from the dispatch when none came) is killed and ended crashed, at that receipt and at the total the reports gave, whatever the provider answers and whatever heartbeats arrive. Every pass of the upkeep checks it, and so does MeetingManager.reconcile. A value that is not a finite number of milliseconds above zero is refused with a RangeError when the manager is built, and so, with a TypeError, is a run store without updateWith (IRunStore.updateWith): the usage reports and the silence's ends are decided on the stored row in the write, which a read followed by an update cannot do.

Optional dispatchGuard

dispatchGuard?: ((run, work) => Promise<void>)

Host serializes dispatch admission with its other sends. It invokes work only when admitted. The manager calls it for each leased job of a run that waits for its dispatch, or whose dispatch is recovered, with the run as leased; work reads the run again and dispatches it. A dispatch it does not admit keeps its lease and is offered again once the lease runs out (leaseTtlMs), or sooner when the host releases the job (IJobStore.release, under the manager's managerId).
