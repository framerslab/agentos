Class SqlCheckpointStore

ICheckpointStore over a @framers/sql-storage-adapter store, with the behaviour of InMemoryCheckpointStore: a checkpoint saved again under its id is overwritten, the most recent checkpoint has the latest timestamp and, of checkpoints with the same timestamp, was saved last, and fork() merges each patchState partition into a copy of the source.

Every save takes the next save_seq, one more than the largest in the table, in the statement that writes the row, and a save under an id that exists takes a new one, so a save that starts after another has finished takes the larger number. A store runs its own saves one after another, in the order they were called, so saves of one store that overlap, as a parallel batch's branches make them, take numbers in that order, as InMemoryCheckpointStore keeps them: the save called last is the most recent, and a resume from it skips every branch it records. Saves of two stores, or two processes, that overlap can take the same number on Postgres; id orders them.

Each statement is one statement, so the store needs no transaction. A read, a save and a delete make the table first unless ensureSchema is false.

Example

import { resolveStorageAdapter } from '@framers/sql-storage-adapter';
import { SqlCheckpointStore } from '@framers/agentos/orchestration/checkpoint';

const db = await resolveStorageAdapter({ filePath: './checkpoints.sqlite' });
const graph = new AgentGraph(state).compile({ checkpointStore: new SqlCheckpointStore({ db }) });

ensureSchema

  • ensureSchema(): Promise<void>

  • Creates the table and its indexes unless the table answers a read already, so a store over a table that exists runs no DDL: on Postgres each CREATE INDEX takes a SHARE lock on the table, which holds back its writes, before it looks for the index's name. Called before the first statement; safe to call again. Does nothing with ensureSchema: false.

    Another session can make the table between the read and the DDL: two stores starting on an empty database both find it missing. On Postgres the DDL of the one that loses then fails once the other commits, IF NOT EXISTS notwithstanding, on the catalogue's unique index or as a duplicate table. The DDL runs again on such a failure, as the memory and learning stores run their schema steps, and finds what the other made, so the table and every index exist when it completes. Any other failure rejects, and the next call tries again.

    Returns Promise<void>

save

  • save(checkpoint): Promise<void>

  • Persist a checkpoint snapshot.

    If a checkpoint with the same id already exists it is overwritten.

    The runtime awaits each save and does not retry one that rejects: the run that asked for the checkpoint ends with the store's error, which GraphRuntime.stream() throws, and a resume by the run id continues from the last checkpoint the store saved. When a save inside a parallel batch rejects, the run ends with the error once the batch's other nodes have finished.

    Parameters

    • checkpoint: Checkpoint

      The snapshot to persist.

    Returns Promise<void>

    Throws
